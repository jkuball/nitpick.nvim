1. INTRODUCTION                                           *nitpick-intro*

Read the code your agent wrote, mark what bothers you, and send it all back
as one review.

Comments are anchored with extmarks, shown in the sign column and as
virtual text. Each instance of Neovim has one review, kept in memory for as
long as it runs. Quitting Neovim drops it, without asking.

Your agent needs nitpick's integration for it (see |nitpick-bridge|); it
listens in every interactive session.

The project root is the nearest directory at or above |:pwd| that contains
one of `root_markers` (|nitpick-config|), else |:pwd| itself. It decides how
paths appear in the review (relative to it) and which agent session |:NitTo|
picks. Files outside of it can be annotated too; you get a warning, and the
review names them by their absolute path.

2. COMMANDS                                               *nitpick-commands*

:[range]Nit[!] [text]                              *:Nit*
    Comment on [range] (default: the current line). With [text], store it
    directly: >vim
        :Nit Explain this condition
        :'<,'>Nit This whole block looks redundant
        :12,18Nit question: why do we need this?
<
    A comment may start with a label (|nitpick-labels|); the first word of
    [text] completes to one.
    Without [text], open a comment buffer. It is an ordinary buffer: |:w|
    saves the comment, |:wq| saves and closes, |:q!| discards. Writing an
    empty buffer deletes the comment. Without a range, an existing comment
    on the cursor line is edited; with a range, the comment on exactly that
    range. [!] always starts a new comment. In a nitpick quickfix or
    location list window, :Nit edits the comment of the entry under the
    cursor – any comment, notes included. Command modifiers choose the
    window: >vim
        :vertical Nit
        :tab Nit
<
:NitNote[!] [text]                                          *:NitNote*
    A note on the review as a whole, not on any line, such as "let's rethink
    the naming overall". Notes come first in the review, under "General".
    Without [text], open the existing note in a comment buffer as |:Nit|
    does – with several, pick one – or start a new one. [!] always starts a
    new one.

:NitFile[!] [text]                                          *:NitFile*
    A note on the current file as a whole, not on any line. It shows as
    virtual text at the end of the file's first line, and in the review
    under the file's heading, before its lines. Without [text] and with
    [!], as for |:NitNote|.

:[range]NitEdit[!]                                          *:NitEdit*
    Edit a comment that touches [range] in a comment buffer, as |:Nit| does.
    Without a range, the comment under the cursor, the most specific
    first: one on the text under the cursor, else one on whole lines, else
    any on the line. With several, pick one; [!] always picks, among all
    comments on the line or [range]. In a nitpick quickfix or location list
    window it edits an entry in [range].

:[range]NitDelete                                          *:NitDelete*
    Delete the comments that touch [range]. In a nitpick quickfix or
    location list window it deletes the entries in [range] instead.

:Nits                                                      *:Nits*
    Put all pending comments into the |quickfix| list and open it. The list
    is kept up to date while it exists, so |]q|, |:cdo| and friends work.

:LNits                                                     *:LNits*
    Put the current file's pending comments into the window's
    |location-list| and open it. Kept up to date like |:Nits|.

:NitReview [text]                                          *:NitReview*
    Open the complete review message in a Markdown buffer. It works like the
    message buffer of `git commit`: edit it freely, |:w| saves, and closing
    the buffer (|:wq|, |:x|, |ZZ|) sends what you saved last. |:q!| before
    saving cancels; to cancel after saving, empty the buffer and |:wq|. If
    sending fails, the buffer opens again with your text. [text] works as
    for |:NitSend|.

:NitSend [text]                                            *:NitSend*
    Send all pending comments. [text] is put in front of the review. The
    agent takes it the most immediate way it has: idle, it starts a turn;
    busy, it takes the review as early as it can (|nitpick-bridge|).
    Comments are only removed once the agent accepted them.

:NitClear[!]                                               *:NitClear*
    Delete all pending comments after confirmation ([!] skips it).

:NitTo[!]                                                    *:NitTo*
    Attach to the agent session reviews go to. If exactly one session runs in
    this project, attach to it directly; otherwise (or with [!]) list all
    running sessions with |vim.ui.select()|, those of this project first.
    Each entry shows the agent, the session's tag – which the agent shows
    too, as "ŋ nvim a3f9c1" – its title and its directory. Before you
    attach, |:NitSend| does the same as |:NitTo|.

3. MAPPINGS                                               *nitpick-mappings*

nitpick maps no keys. It provides <Plug> targets; this is a suggested set,
with "gb" ("go bother") as the operator: >lua
    local map = vim.keymap.set
    map({ "n", "x" }, "gb", "<Plug>(nitpick-annotate)")
    map({ "n", "x", "o" }, "]n", "<Plug>(nitpick-next)")
    map({ "n", "x", "o" }, "[n", "<Plug>(nitpick-prev)")
    map("n", "<leader>nn", "<Plug>(nitpick-annotate-line)")
    map("x", "<leader>nn", "<Plug>(nitpick-annotate)")
    map("n", "<leader>no", "<Plug>(nitpick-note)")
    map("n", "<leader>nf", "<Plug>(nitpick-file)")
    map({ "n", "x" }, "<leader>ne", "<Plug>(nitpick-edit)")
    map({ "n", "x" }, "<leader>nd", "<Plug>(nitpick-delete)")
    map("n", "<leader>nq", "<Plug>(nitpick-qflist)")
    map("n", "<leader>nl", "<Plug>(nitpick-loclist)")
    map("n", "<leader>nr", "<Plug>(nitpick-review)")
    map("n", "<leader>ns", "<Plug>(nitpick-send)")
    map("n", "<leader>nc", "<Plug>(nitpick-clear)")
    map("n", "<leader>nt", "<Plug>(nitpick-to)")
<
  <Plug>(nitpick-annotate)       Operator: annotate {motion}, or the selection
  <Plug>(nitpick-annotate-line)  Annotate [count] lines
  <Plug>(nitpick-note)           |:NitNote|
  <Plug>(nitpick-file)           |:NitFile|
  <Plug>(nitpick-edit)           |:NitEdit| under the cursor or in the selection
  <Plug>(nitpick-delete)         |:NitDelete| on the line or selection
  <Plug>(nitpick-qflist)         |:Nits|
  <Plug>(nitpick-loclist)        |:LNits|
  <Plug>(nitpick-review)         |:NitReview|
  <Plug>(nitpick-send)           |:NitSend|
  <Plug>(nitpick-clear)          |:NitClear|
  <Plug>(nitpick-to)             |:NitTo|
  <Plug>(nitpick-next)           Next nit in the buffer
  <Plug>(nitpick-prev)           Previous nit in the buffer

"gbb" annotates the current line, like "gcc": the second "b" is the
`line_key` option. If you put the operator elsewhere, set `line_key` to its
last key. Don't end the operator's keys in "a" or "i", which start text
objects ("ap", "iw").

Linewise motions and Visual-line mode comment on whole lines. Charwise ones
("gbiw", "v" selections) also remember the exact columns: the text is
highlighted with `NitpickRange`, and the review names the columns ("line 9,
columns 5-9") while still quoting whole lines.

Next/previous take a [count], wrap around, set the ' mark and work in Visual
and Operator-pending mode. Across files, use |:Nits| and |]q|.

Note: vim-unimpaired uses "]n" and "[n" for conflict markers.

4. CONFIGURATION                                          *nitpick-config*

No setup is needed. Options come from `vim.g.nitpick` or from: >lua
    require("nitpick").setup({
      line_key = "b",              -- gb + b: current line
      open_cmd = "botright 10split",
      startinsert = true,
      signs = { enabled = true, single = "ŋ", first = "ŋ", middle = "│", last = "└" },
      icon = "ŋ",                  -- statusline and window titles
      virt_text = { enabled = true, prefix = "ŋ ", max_width = 60 },
      instructions = "…",          -- opening text of every review
      labels = { … },              -- see |nitpick-labels|
      max_excerpt_lines = 200,
      root_markers = { ".git", ".jj", ".hg" },
      socket_dir = nil,            -- see |nitpick-bridge|
      timeout = 2000,
    })
<

A project replaces the opening instructions with `.pi/review-prompt.md` in
its root; an empty file omits them.

                                                          *nitpick-labels*
A comment may start with a Conventional Comments label
(https://conventionalcomments.org), optionally with decorations: >
    question: why a loop and not sum()?
    suggestion (non-blocking): rename x to total
<
The label tells the agent what you want without rules in the prompt: it is
part of the comment's text. nitpick shows it as a sign beside the comment,
highlights it in the comment buffer in the same color and completes it there
with its 'omnifunc' (|i_CTRL-X_CTRL-O|, or a completion plugin's omni
source); both come from the "nitpick" ftplugin. `labels` lists the known
ones; setting it replaces the whole list. The defaults: >lua
    labels = {
      { name = "praise",     sign = "+", hl = "DiagnosticSignOk" },
      { name = "nitpick",    sign = "~", hl = "NitpickSign" },
      { name = "suggestion", sign = ">", hl = "DiagnosticSignInfo" },
      { name = "issue",      sign = "!", hl = "DiagnosticSignWarn" },
      { name = "todo",       sign = "*", hl = "DiagnosticSignWarn" },
      { name = "question",   sign = "?", hl = "DiagnosticSignHint" },
      { name = "thought",    sign = "-", hl = "NitpickSign" },
      { name = "chore",      sign = "c", hl = "NitpickSign" },
      { name = "note",       sign = "i", hl = "DiagnosticSignInfo" },
    },
<

Highlights: `NitpickSign`, `NitpickVirtText`, `NitpickTitle`, `NitpickRange`.
A label's `hl` colors its sign and the label in the comment buffer.

Comment and review buffers have the filetype "markdown.nitpick": Markdown,
plus "nitpick" for configuring them apart. Their title is the 'winbar'; a
plugin that draws its own winbar replaces it unless told to skip them, e.g.
lualine: `options = { disabled_filetypes = { winbar = { "nitpick" } } }`.

Statusline: `require("nitpick").status()` returns e.g. "ŋ 3 → a3f9c1"
(pending comments, attached session), or "" when there is neither. For
lualine: `sections = { lualine_x = { require("nitpick").status, … } }`.

5. HOW IT TALKS TO THE AGENT                              *nitpick-bridge*

Each agent session listens on a Unix socket `<pid>.sock` in
`$NITPICK_DIR`, else `$XDG_RUNTIME_DIR/nitpick`, else
`$TMPDIR/nitpick-<uid>`. The directory is private (0700). Requests are
newline-delimited JSON. Neovim formats the review, so |:NitReview| shows
exactly what the agent receives. In Pi, `/nvim [on|off]` shows or toggles the
bridge; `NITPICK_AUTOSTART=0` disables the automatic start.

Claude Code (2.1.287 or newer) works the same way through the mod in the
repository's `integrations/claude/` directory: it starts the same bridge in a
Node process for each session. |:NitTo| lists such sessions as "claude <tag>",
and Claude Code shows the tag among the mode labels right of its prompt.

The protocol, version 1, has two requests. Neovim connects, writes one JSON
line, reads one JSON line back, and the connection closes: >json
    → {"v":1,"type":"hello"}
    ← {"ok":true,"v":1,"type":"hello","pid":4242,"session":{"agent":"pi",
       "id":"…","short":"1bca14","name":"…","cwd":"/work","idle":true}}

    → {"v":1,"type":"submit","text":"<the review>","comments":3}
    ← {"ok":true,"v":1,"type":"submit"}

    ← {"ok":false,"v":1,"error":"…"}
<
Neovim formats the whole review; an agent only delivers `text`. `comments`
is for the agent's own notification.

Run |:checkhealth| nitpick to see the sessions Neovim can reach.
